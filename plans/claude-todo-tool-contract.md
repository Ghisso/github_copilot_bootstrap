# Big Plan: claude-todo-tool-contract

## Context

A consumer repository generated by this bootstrap reported a failing tool call
from a generated Claude Code subagent:

```text
Error: No such tool available: TodoWrite. TodoWrite is disabled for this session, in subagents as well as here.
```

The generator maps the abstract `todo` capability to the Claude tool name
`TodoWrite` (`scripts/generate_targets.py`, `CLAUDE_TOOL_MAP`) and writes that
name into generated Claude agent frontmatter through `render_claude_agents()`.
Three agents rendered for the `claude-code` target declare `todo`: `coder`,
`orchestrator`, and `planner`.

The cause was confirmed against the installed Claude Code binary
(`~/.local/share/claude/versions/2.1.226`) and the current official
documentation (`code.claude.com/docs/en/tools-reference`, `subagents`,
`env-vars`). `TodoWrite` is not an obsolete or misspelled name. It is a real
tool that the runtime does not enable:

- The binary defines `TodoWrite` and the four task tools as mutually exclusive.
  `TodoWrite.isEnabled()` returns `!mO() && !Sse()`; `TaskCreate.isEnabled()`
  returns `mO() && !Sse()`; and `mO()` returns false only when
  `CLAUDE_CODE_ENABLE_TASKS` is set to false. The variable defaults to on, so
  `TodoWrite` is off by default and the task tools take its place.
- Claude Code v2.1.233 and later leave out all five names — `TodoWrite`,
  `TaskCreate`, `TaskGet`, `TaskUpdate`, and `TaskList` — on Opus 4.8,
  Sonnet 5, Fable 5, Mythos 5, and later versions of those families unless the
  user sets `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`.
- The error text itself is the runtime's generic "exists but is not enabled"
  branch, not a "no such name" branch.

`TaskCreate`, `TaskGet`, `TaskList`, and `TaskUpdate` are not a usable
replacement in generated frontmatter. Subagents run in the background by
default, and the documented background filter keeps only a fixed set of
built-in tools. That set includes `TodoWrite` but excludes the four task
tools, which Claude Code removes from a background subagent "whether inherited
or listed in the `tools` field". Only teammates in agent teams keep them. The
documentation states the same conclusion directly: in a session without the
task tools, Claude Code does not provide the task tools to subagents either.

The practical result is that a generated Claude subagent has no working written
task-tracking tool on current models, and no tool name in the `tools:` field
can change that. The bootstrap must stop promising one.

### A wider finding in the same map

While specifying the regression check, two further names in `CLAUDE_TOOL_MAP`
were found to be suspect. Both are emitted into generated frontmatter today,
so `todo` may not be the only instance of this bug:

- **`MultiEdit`** (from the `edit` capability) does not appear anywhere in the
  documented tool table, and the installed binary contains the string only
  inside permission-rule validation and a trust-dialog set of mutating tool
  names — never as a tool definition. It appears to be a removed tool whose
  name survives only for backward-compatible permission rules.
- **`Task`** (from the `delegate` capability) is not the documented name; the
  table lists `Agent` for spawning a subagent, and the binary holds
  `var yi="Agent"` with no `aliases` array. Telemetry code checks
  `e!=="Agent" && e!=="Task"` together, which suggests the old name is
  tolerated on some path, but static inspection cannot prove that a `tools:`
  entry of `Task` still resolves.

Static analysis is not sufficient to settle either name. Both must be resolved
against a live runtime during implementation, because the consequence differs:
a name that no longer resolves is silently dropped from the agent's tool list,
which removes a capability the prompt still assumes.

## Goals

- Stop emitting a tool name into generated Claude agent frontmatter that the
  runtime does not provide.
- Keep the canonical instruction text runtime-neutral, so no prompt commands an
  agent to call a tool that may be absent.
- Add validation that fails the build when generated Claude frontmatter names a
  tool outside a reviewed allowlist, so this class of drift cannot regenerate.
- Resolve the `MultiEdit` and `Task` names against the live runtime and correct
  `CLAUDE_TOOL_MAP` wherever the runtime does not provide the emitted name.
- Preserve the abstract capability model, and preserve the `todo` capability's
  existing meaning for GitHub Copilot, OpenAI Codex, and Google Antigravity.
- Change no consumer environment variables and require no consumer opt-in.

## Design Overview

Remove the `"todo"` entry from `CLAUDE_TOOL_MAP` in
`scripts/generate_targets.py`. The `todo` capability then has no Claude tool
mapping, `render_claude_tools()` skips it through its existing
`CLAUDE_TOOL_MAP.get(capability, [])` default, and generated Claude frontmatter
stops naming `TodoWrite`. No `agent.yaml` file changes.

This follows a pattern the repository already uses deliberately. The `vscode`
capability is Copilot-only and is intentionally absent from the other tool
maps, with the reason recorded in a comment directly above the maps. The
`todo` capability is already absent from `ANTIGRAVITY_TOOL_MAP`, and
`tests/test_validate_targets.py` already asserts that `todo` does not appear in
a rendered Antigravity adapter. Claude Code becomes the second runtime where
`todo` is an abstract intent with no native tool, which is exactly what the
runtime now reports.

The three affected agents keep non-empty tool lists after the change, which
was verified against their current capability lists. This matters because a
`tools:` field that resolves to nothing is a documented Claude Code error.

The canonical instruction text must stop naming the tool. Two lines in
`shared/policies/workflow.instructions.md` name `TodoWrite` directly. They will
be reworded to the runtime-neutral phrasing that
`shared/agents/orchestrator/prompt.md` already uses: use the runtime's native
task tracker when one is available, and otherwise write the same checklist as
prose. That prompt needs no change; it is already correct.

Regression coverage mirrors the existing Antigravity precedent. Antigravity
validation builds `ANTIGRAVITY_ALLOWED_TOOLS` from its capability map and
reports "unknown native tools" for anything outside it. Claude validation gains
an equivalent reviewed allowlist and a subset check on the `tools:` line, added
to the Claude agent frontmatter loop in `scripts/validate_targets.py` that
already extracts that line for the Semble and Context Mode check. The allowlist
is a reviewed constant rather than a derivation from `CLAUDE_TOOL_MAP`, because
deriving it from the map would make the check pass for any name the map
contains and would therefore not have caught this bug.

### Rejected alternatives

- **Map `todo` to the four task tools.** Rejected. Background subagents have
  them removed regardless of the `tools:` field, so this moves the failure
  rather than fixing it, and it would emit four unusable names instead of one.
- **Remove `todo` from the three agents' `capabilities` lists.** Rejected. It
  edits three `agent.yaml` files to express one runtime's limitation, and it
  would silently remove the capability from Copilot, where it still maps to
  real tools.
- **Tell consumers to set `CLAUDE_CODE_ENABLE_TASKS=0` or
  `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`.** Rejected as the fix. It pushes runtime
  configuration onto every consumer to keep a tool the prompts do not require,
  and on current models the first variable alone does not restore the tool.
  The limitation will be documented instead.

## Non-Goals

- Do not add `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, or `TaskStop`
  to any tool map.
- Do not set, recommend, or generate `CLAUDE_CODE_ENABLE_TASKS` or
  `CLAUDE_CODE_ENABLE_TODO_TOOLS` in generated settings or the devcontainer.
- Do not change `COPILOT_TOOL_MAP`, `ANTIGRAVITY_TOOL_MAP`, the Codex
  capability prose, or any other runtime's mapping.
- Do not restructure the abstract capability model or the `AGENT_CAPABILITIES`
  allowlist.
- Do not change `shared/agents/orchestrator/prompt.md`, which is already
  runtime-neutral.
- Do not hand-edit `dist/multi-agent/` or the installed generated adapters.
- Do not add task-tracking behavior to hooks as a replacement mechanism.

## Phases

- [ ] `2026-09-09_phase-A-claude-todo-tool-contract` — drop the Claude `todo`
  mapping, reword the two canonical instruction lines, add the Claude tool
  allowlist check, regenerate, and document the runtime limitation.

One phase is deliberate. The generator change and the instruction change are
two halves of one contract: shipping either alone leaves generated output and
canonical instructions contradicting each other, and both halves regenerate
`dist/multi-agent/`. The plan-decomposition skill's split criteria are all
absent here — no dependency stages, no differing verification, no phase over
300 lines, and no valuable partial delivery — and its rule that steps which
must happen atomically belong in the same phase applies directly. This also
matches the recorded lesson that configuration and validator allowlist
migrations should be one atomic phase when the new validation rejects the old
contract, so every phase boundary stays green.
