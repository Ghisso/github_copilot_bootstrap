# Source, generated output, consumer repo, and nested AI state

Source, tests, and the policies under `shared/policies/` outrank this page.
Where this page and the code disagree, the code is right.

## Four places, four different owners

This repository is not an application. It is a source-of-truth plus
generated bootstrap for AI coding agents, and understanding it means
keeping four locations distinct:

| Place | What it holds | Who edits it |
|---|---|---|
| `shared/` in this repository | policies, agent metadata and prompts, skills, hooks, MCP definitions, templates, the verifier and findings recorder, memory seed, state READMEs, devcontainer, schemas | bootstrap maintainers, by hand |
| `dist/multi-agent/` in this repository | the single installable target rendered from `shared/` | nobody; regenerated by `scripts/generate_targets.py --all` and gitignored |
| a consumer's outer repository | thin root adapters (`AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.github/**`, `.codex/**`, `.agents/**`, `.vscode/**`) plus the installed `.claude/` basis | the installer writes adapters; the consumer edits only its project context and its own state |
| the nested `.claude/` repository | a separate Git repository on branch `ai-state` holding the installed basis and the mutable AI state (memory, plans, session logs, quality reports, findings, receipts) | hooks and the installer commit it; the outer repository ignores it |

The authoring repository's own root `.gitignore` states both boundaries:
`dist/` is generated build output, and `.claude/` is tracked in the nested
repository, not the outer one.

### Authoring repository versus consumer

Two facts about this repository do not carry over to consumers. First, the
tracked root `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, and `.codex/config.toml`
here are authoring versions, kept byte-stable across self-refreshes; in a
consumer they are generated adapters that must not be hand-edited. Second,
this repository installs its own generated output into itself
(`scripts/install_bootstrap.py . --local-only --allow-self`) so the whole
lifecycle can be exercised end to end. A normal consumer never sees
`shared/`; it receives only the rendered copy. See
[Installing the bootstrap, file ownership, and runtime drift checks](/openwiki/operations/install-ownership-and-runtime-checks.md)
for the install and refresh mechanics.

## What `shared/` contains

- `shared/policies/*.instructions.md`: workflow, workspace, quality and
  testing, code standards, config-first design, tool routing, agent
  reporting, API and deployment guidance. Each has target-neutral
  frontmatter declaring `applicability: always` or a list of path patterns.
- `shared/agents/<id>/`: JSON metadata in `agent.yaml` plus canonical or
  provider-specific prompt bodies. See
  [Agent roster, prompts, and the skill library](/openwiki/architecture/agents-and-skills.md).
- `shared/skills/<name>/SKILL.md`: the skill library, with
  `visibility: public|background`.
- `shared/hooks/`: `hooks.json` (the Copilot hook configuration), the
  `scripts/` guardrails, and `git-hooks/`.
- `shared/mcp/servers.json`: the shared MCP server definitions, currently
  `semble` (through `uvx`), `context-mode` (routed through
  `context-mode-dispatch.sh server`), and `context7`.
- `shared/scripts/verify.py` and `shared/scripts/record_findings.py`: the
  deterministic verifier and findings recorder, copied into every
  consumer's `.claude/scripts/`.
- `shared/templates/`, `shared/MEMORY.md`, `shared/review-profiles/`,
  `shared/prompts/`, `shared/schemas/`, `shared/devcontainer/`,
  `shared/vscode/tasks.json`, and the `plans/`, `quality_reports/`, and
  `session_logs/` README seeds.

## How generation works

`scripts/generate_targets.py` has exactly one target, `multi-agent`.
`generate` resets the output directory, calls `render_multi_agent`, and
strips any quarantined content. `render_multi_agent` runs a fixed sequence:

1. `render_devcontainer`: the trackable `.devcontainer/` GPU sandbox.
2. `render_shared_basis`: the `.claude/` basis. It copies `MEMORY.md`,
   templates, `verify.py`, `record_findings.py`, and the policies into
   `.claude/instructions/`, renders Claude path-scoped rules for
   conditional policies, and copies `runtime_ownership.py` and
   `validate_plan_frontmatter.py` verbatim because they are target-neutral
   authorities that provider path rewriting would corrupt. It also writes
   `bootstrap-ownership.env`, the inert manifest of installer-owned root
   adapters.
3. Root `AGENTS.md` from `render_root_guidance("multi-agent")`.
4. `render_github`: `.github/copilot-instructions.md`, one instruction
   adapter per policy, the copied `hooks.json`, `.vscode/mcp.json`,
   `.vscode/tasks.json`, and one `.github/agents/<id>.agent.md` per
   eligible agent.
5. `render_claude`: `CLAUDE.md` from `render_root_guidance("claude-code")`,
   `.mcp.json`, and `.claude/settings.json` with the hook wiring.
6. `render_codex`: `.codex/config.toml` (MCP servers plus one
   `[[skills.config]]` entry per skill), `.codex/hooks.json`, and one
   `.codex/agents/<id>.toml` per eligible agent.
7. `render_antigravity`: a copy of the skill tree under `.agents/skills/`,
   `.agents/mcp_config.json`, `.agents/hooks.json`, and one
   `.agents/agents/<id>/agent.md` per eligible agent.

Text copied into a target passes through `transform_target_paths`, a table
of literal replacements per provider: for Claude Code,
`.github/copilot-instructions.md` becomes `CLAUDE.md` and `.github/hooks`
becomes `.claude/hooks`; for Codex the same sources become `AGENTS.md` and
`.codex/hooks`. This is how one canonical policy text can name "the root
guidance file" correctly on every host.

The generated tree is never edited by hand. The rule enforced by
`validate_determinism` is that a fresh `generate_targets.py --all` into a
temporary directory must byte-match the current `dist/`, so any hand edit to
`dist/` fails validation on the next run.

## What the validator proves

`scripts/validate_targets.py` is the structural gate over `dist/`. Its
`main` runs, in order: the task-lane contract, the Codex model contract,
agents, MCP and hook wiring, the Antigravity manifest and skills, the
Context Mode tool surface, skills and paths, docs parity (which owns the
skill-library integrity rules), memory security authority, routing-table
parity, root-source mirror cases, runtime drift cases, the Ponytail diff
classifier, the typo-bypass path restriction, end-to-end receipt-chain
lifecycle cases, stale-receipt rejection, single-phase terminal
publication, JSON report readers, devcontainer and installer, state sync,
installer commit failure, local-only state sync, determinism, and finally
the presence of hook-gate regression tests. Any failure prints `FAIL ...`
lines and exits 1; success prints
`PASS generated target is structurally valid`.

Many of these gates run real subprocesses in temporary repositories
(installer, state sync, receipt chains), which is why the validator is slow
and why it is a required item in every phase's verification block rather
than a unit test.

## Policy discovery per host

Policies are authored once and discovered natively per host. Claude Code
loads conditional policies as path-scoped rules under `.claude/rules/`;
always-on policy stays in the concise root guidance. Codex reads
hierarchical `AGENTS.md` files with a combined size cap, so a conditional
policy becomes a nested `AGENTS.md` only when it owns a stable concrete
directory, and otherwise maps to an existing skill. GitHub Copilot's
instruction adapters derive `applyTo` from the same patterns, and generation
checks their scope parity with Claude's `paths`. Runtime loading by a real
client is probed separately by `scripts/check_native_clients.py`, not
claimed by the structural validator.

## Representative tests

`tests/test_validate_targets.py` exercises the generator and validator
together: agent target scoping and rendering, the Antigravity static
adapter, Codex specialist metadata, skill-contract checks, and the README
agent contract. The validator's own end-to-end cases (receipt chains,
installer, state sync) are part of `validate_targets.py` itself and run
under `uv run python scripts/validate_targets.py`.
